## Decisions (with reasons)

**A. What to record: processed voice only (post-limiter), no "mic-heard mix".** The MR plays in another app: Android `AudioPlaybackCapture` needs a MediaProjection consent dialog per session and apps can opt out (`allowAudioPlaybackCapture=false`; YouTube/Melon are known to) and iOS has no app-to-app capture (unverified wording, well-known platform limits). A "mix" built from the raw mic would just be the same voice plus room-bleed MR at speaker volume — low value, and it doubles the writer path. Recording the exact buffer that reaches the speaker is one copy per callback and matches the request "as heard with our effects".

**Format: Android WAV 16-bit PCM written by a C++ writer thread; iOS AAC .m4a via `AVAudioFile` from an `installTap` on the limiter node.**
- Android: a lock-free SPSC float ring (new `android/app/src/main/cpp/recorder.h`, platform-agnostic, same style as `triple_buffer.h`) is filled by `runDsp()` after `comp_.limit()`; a `std::thread` drains it every 20 ms to `fwrite`. WAV is ~40 lines; MediaCodec+MediaMuxer would need PCM to cross JNI and a second thread/state machine. Size: 48 kHz mono int16 = 5.8 MB/min; cap 10 min (= 58 MB) + free-space check. Optional later step transcodes WAV -> M4A with MediaCodec off the realtime path (Step 10, optional).
- iOS: the true output includes `AVAudioUnitEQ -> AVAudioUnitReverb -> limiter`, which run inside the AVAudioEngine graph *after* `renderSource` (AudioEngine.swift:741-751 only covers HPF..freqShifter). The only place the heard signal exists is `limiter`'s output bus, so record with `limiter.installTap(onBus: 0, ...)` and `AVAudioFile(forWriting:settings:)` using `AVFormatIDKey: kAudioFormatMPEG4AAC`. Apple's tap block runs on a non-realtime internal thread with its own buffering, so file writes there are the documented pattern (unverified against current docs; this is the classic Apple "record with a tap" sample). No shared C++ needed on iOS for recording — it is platform I/O, not DSP.
- Dart lists both extensions (`.wav`/`.m4a`).

**Files**: Android `context.filesDir/recordings/`, iOS `Documents/Recordings/` (not exposed to Files app; `UIFileSharingEnabled` is not set in Info.plist). Name `yyyyMMdd_HHmmss.ext`. Native exposes `recordingsDir` once; Dart does list/delete/rename with `dart:io`. Playback via `audioplayers` (new dep) only while the engine is stopped (avoids AVAudioSession category fights on iOS); share via `share_plus` (new dep — pubspec.yaml:11-20 has neither; `path_provider` not needed).

**Lifecycle**: recording is owned by the native engine and dies with the streams: Android `closeStreams()` (audio_engine.cpp:206-227 → `recorder_.stop()`), iOS `internalStop()` (AudioEngine.swift:477-515 → `stopRecording()`). Reconnect / speaker-mode reopen / stop all go through those, so recording ends cleanly and the plugin's existing 50 ms poll (AudioEnginePlugin.kt:172-195, AudioEnginePlugin.swift:126-146) notices `isRecording` flipped and emits `{'type':'record','recording':false,'path':..,'durationMs':..,'reason':'engine'|'cap'|'user'}`. Dart logs `record_stop` from that single event path on both platforms. FGS: unchanged — recording only runs while the mic FGS (type microphone) is up; no new permission (app-private storage, API 29+ needs none; `minSdk = flutter.minSdkVersion` = 21 (unverified), app-private dir needs no permission on any API).

**Privacy/store**: docs/privacy.html:14 says "녹음하거나 저장하지 않으며" — must change to: recordings are made only when the user taps 녹음, stored only on the device in the app's private folder, never uploaded, deletable in-app (Step 9). Play Data safety / App Store privacy labels: on-device-only user files that the developer never receives are not "collected", so no label change is expected (unverified; owner to confirm in the consoles).

**B. Auto-tune: ONE shared C++ header `pitch_corrector.h`, compiled on iOS through an Objective-C++ shim.** Requirements: iOS deployment 16.0 (pbxproj:293), bridging header exists (pbxproj:366,389 → `Runner/Runner-Bridging-Header.h`), `CLANG_CXX_LANGUAGE_STANDARD = "gnu++0x"` (pbxproj:252,307 and the third config) must become `"gnu++17"`, and `HEADER_SEARCH_PATHS` must add `$(SRCROOT)/../android/app/src/main/cpp`. A `.mm` file (`ios/Runner/DspBridge.mm`) with a plain C API declared in `ios/Runner/DspBridge.h`, `#import`ed from the bridging header, is callable from Swift with no SwiftPM/Podfile change. This is the repo's "no duplicated logic" path; duplicating in Swift (as the 5 existing DSP files do) is the alternative explicitly rejected here.

Algorithm (CPU and latency budget): **YIN pitch detection** (de Cheveigné & Kawahara 2002) on a 1024-sample window at 48 kHz (21 ms), hop 256, lag range 48..600 samples (80–1000 Hz), threshold 0.15, parabolic refinement; ~1024*552 MAC per hop ≈ 100 M MAC/s worst case — too much for armeabi-v7a, so compute the difference function on a 2x decimated copy (window 512, lags 24..300 → ~25 M MAC/s) and refine on the full-rate signal around the found lag. **Pitch shifting: Lent's pitch-synchronous overlap-add from a delay line** (K. Lent, "An efficient method for pitch shifting digitally sampled sounds", Computer Music Journal 13(4), 1989; the method zita-at1 uses — reference the method, do not copy GPL code): grains of 2 periods, Hann window, read from a circular delay line and retriggered every *output* period = input period / ratio. Latency ≈ 1 input period (≤ 12.5 ms at 80 Hz) — vs a phase vocoder (FFT 1024–2048 + hop ⇒ 40–80 ms, and phasiness on voice). Retune: target = nearest scale note (chromatic default; `setScale(mask12)` for later keys), ratio = target/detected, smoothed with a one-pole whose time constant is the "retune speed" (default 5 ms ≈ hard T-Pain; 1.0 ratio when unvoiced/aperiodicity > threshold). Momentary: `setHold(bool)` from the control thread; audio thread ramps a wet gain over 20 ms (linear, per-sample) and mixes `dry*(1-w) + shifted*w`; when `w` reaches 0 the shifter stops running (CPU) and resets on the next press. Chain position: **after compressor, before echo** (HPF→Gate→Comp→**Tune**→Echo→…), so echo/reverb tails repeat the corrected note; audio_engine.cpp:229-251 and AudioEngine.swift:741-748.
